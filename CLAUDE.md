# BI Agent MVP — guidance for Claude

A natural-language BI agent: users ask questions in plain English and get a grounded answer, the SQL, a table and a chart. Built in small, verified milestones (M1–M27). `README.md` covers setup and usage; this file covers how to work on the code.

## Keep the docs current

- `docs/build-plan.html` is the living plan: roadmap, step-by-step milestone guides, development log, known limits. Update it whenever the plan changes, a milestone starts or finishes, a decision is made, or a new limit appears. Keep the "Last updated" line and the development log current, and label results as **seen** (output observed) or **reported** (the owner said so).
- Edit it in place; git keeps history. Never create new `_vN` copies. The older `docs/BI Agent MVP_ incremental build plan*.html` files are historical only.
- Update `README.md` when setup steps, configuration, API routes, roles or user-visible behavior change. Its **Features** section is the canonical list of what the project offers: add to it whenever a feature lands.
- Update this file when conventions, layout or status change.

## Test-driven development (always)

Every change to behaviour follows red, green, refactor:

1. **Red:** write or update the test first. Run it and confirm it fails, and fails for the expected reason (not a typo or import error in the test itself, unless the module genuinely doesn't exist yet).
2. **Green:** write the smallest code change that makes it pass. Run the full suite, not just the new test.
3. **Refactor:** tidy up only while every test stays green.

- A bug fix starts with a test that reproduces the bug.
- Show the owner both runs: the failing output and the passing output.
- Never weaken, skip or delete a test to make it pass. If a test is wrong, say why before changing it.
- Exempt: documentation-only changes and configuration with no behaviour. Scratch experiments may skip TDD but are never committed without tests.

## Working rules

- One milestone at a time: explain why, make the smallest change, run the tests, then stop and wait for the owner's approval before starting the next milestone.
- Never claim a test passed unless its output was observed. Say "expected" otherwise.
- Diagnose from real error output before changing code. Never edit a failing test to make it pass; find out why behavior changed.
- Add a dependency only when the current milestone needs it.
- The LLM never enforces authorization. Generated SQL never runs without the validator and the role's read-only database login.
- Secrets stay out of source. `.env` is git-ignored. `docker compose config` prints real secrets — never paste its output. Never print tokens or passwords.
- Before every commit, check `git status` for `.env`, `.venv`, `__pycache__`, `.DS_Store`. One commit per milestone or sub-milestone, conventional messages (`feat:`, `fix:`, `test:`, `refactor:`, `chore:`, `docs:`).
- The owner is learning as they build: explain decisions briefly, give exact commands for macOS/zsh, and say what output to expect.

## Commands

```bash
docker compose up --build -d                      # backend :8000, frontend :8501, db host :5433
docker compose exec backend python -m app.cli create-user <name> <analyst|limited>
cd backend  && .venv/bin/python -m pytest         # integration tests need the db container
cd backend  && .venv/bin/python -m pytest -m "not integration"
cd frontend && .venv/bin/python -m pytest
docker compose exec -T db psql -U admin -d postgres < db/init/<file>.sql   # apply new init SQL to a running db
cd backend && set -a && source ../.env && set +a && .venv/bin/python -m evals.run [--repeat 3] [--case ID]   # real-model evaluation (costs tokens on OpenRouter)
cd backend && LLM_PROVIDER=ollama LLM_TIMEOUT_SECONDS=120 .venv/bin/python -m evals.run --repeat 3   # same, on the local model (free; about 4 minutes)
cd backend && .venv/bin/python -m retail.load --scale full   # rebuild the retail demo database (~20 s; scales: tiny, small, full)
```

Code changes need `--build`; `.env` or compose environment changes need the container recreated.

## Architecture

- Logs are one JSON object per line: log with a short message and `extra={...}` fields (`request_id`, `username`, ...), not formatted strings, for anything worth searching.
- `backend/catalog/*.toml` (one file per business area, plus `metrics.toml`): descriptions, grain, caveats, allowed values, units and `pii` flags for every retail table and column. `app/catalog.py`: strict `load()`, `introspect(run)` (types, keys, relationships, row counts from the database, through any `run(sql, params)` function, so it never imports the driver) and `drift()`. Tests fail if the catalog and the database disagree, or if `pii` flags differ from what `grants.sql` withholds from analysts. Describe every new column there. `catalog.merged()` is the full catalog (types, nullability, keys, foreign keys, referenced-by, descriptions); `python -m retail.export_catalog` writes `catalog/generated/catalog.json` and `docs/data-catalog.html`, and tests fail if they are stale, so regenerate after any catalog or schema change.
- `backend/knowledge/` (RAG R1): business documents (metrics, rules, validated SQL, dashboards, data quality, narratives) as Markdown with a TOML header between `+++` lines; `app/knowledge/documents.py` loads them strictly (ids match file names, one authoritative definition per metric, superseded documents point to a newer active one, access groups match the tables each group may read, no duplicate content). SQL examples are executed by tests. Plan: `docs/rag.html`.
- `app/knowledge/chunking.py`, `store.py`, `ingest.py` (RAG R4): chunk per document type, write the index with the `knowledge_writer` login (`KNOWLEDGE_DATABASE_URL`), incremental by fingerprint; command `python -m app.knowledge.ingest [--rebuild]`. Ingestion tests use a throwaway `knowledge_test` schema; never point tests at `knowledge`. Re-run ingestion after editing `backend/knowledge/`.
- `app/knowledge/embeddings.py` (RAG R3): `OllamaEmbedder` (nomic-embed-text, task prefixes, batches of 32, strict checks) and `FakeEmbedder` (deterministic, for tests); `get_embedder()` reads `EMBEDDING_PROVIDER` (ollama or fake), `EMBEDDING_MODEL`, `OLLAMA_BASE_URL`; dimensions from `[knowledge] embedding_dimensions` in the policy, which must equal `vector(768)` in `08_knowledge.sql`.
- `app/knowledge/retrieval.py` (RAG R5): `retrieve(question, role, ...)` → `Hit`s; `store.Reader.search` filters status, role, embedding model and type in SQL. `[knowledge] min_similarity = 0.60` is calibrated for nomic-embed-text (relevant ≥ 0.649, off-topic ≤ 0.556); recalibrate after changing the embedding model. Fake-embedder tests pass `min_similarity=0.0` because fake scores are not comparable. `evals/retrieval.py` + `evals/retrieval_cases.json` (38 cases): run it after editing the knowledge pack, chunking or retrieval.
- Knowledge answers (demo gap D7, RAG R6b): `coordinator.is_about_knowledge` (patterns: how is X defined, what does X mean, why did, what happened, what is our policy, ...) routes to `knowledge` only when a knowledge function exists and the catalog intent is none or the metric list (table and column questions stay catalog). Path: `find_knowledge` (no hits → hands back to catalog or data via `knowledge.after_find`) → `analyst.explain_knowledge` → `analyst.check_citations` (needs at least one citation, only of retrieved ids, numbers only from the documents; else `knowledge_excerpt` = the best document as plain text; `NOT_FOUND` → plain fallback). Audited as `knowledge_question`. The cite-every-sentence instruction comes last in `knowledge_prompt`: 15/15 cited versus 12/15 when it came first. The frontend renders these as an info note with the Sources line.
- MCP server (demo gap D10): `app/mcp_server.py` (`mcp==2.3.0`, in `requirements-mcp.txt`, host only, not in the image; MCP 2.x names: `MCPServer`, `mcp.server.mcpserver.exceptions.ToolError`). Two tools, `ask_data` and `search_knowledge`, both through `BackendClient`, which signs in with `BI_AGENT_USERNAME`/`BI_AGENT_PASSWORD`, renews an expired token once and turns every failure into a plain `ToolError` (never the password). The backend route `GET /knowledge/search` (signed in, role-filtered via `get_knowledge`, audited `knowledge_search`) serves the second tool. Tests use `httpx.MockTransport`; `tests/test_mcp_server.py` skips if `mcp` is not installed.
- Shared state (demo gap D11): `STATE_STORE=memory|postgres` (`appdb.state_store()`; code default memory, Compose default postgres). `conversation.from_env()`, `throttle.from_env()` and `budget.from_env()` pick `appdb.PgConversationStore`, `PgLoginThrottle` and `PgTokenLedger` (in `appdb.py`, so GR-SQL-06's driver list is unchanged). Times are Unix seconds from an injectable clock (the Postgres budget uses wall-clock time). Conversation appends and trims are single statements, so concurrent instances keep every turn. Tests use keys and usernames starting `d11test` and delete them.
- Retry and circuit breaker (demo gap D9): `llm/resilience.py` `RetryingLLM` (one retry after `delay * attempt` seconds for any `LLMError` except budget, config and timeout) inside `CircuitBreaker` (opens after `LLM_BREAKER_FAILURES` failures in a row for `LLM_BREAKER_COOLDOWN_SECONDS`, raises `LLMUnavailableError` → 503; a half-open trial call closes or reopens it; our own `LLMBudgetError` never counts). `llm/__init__._resilient` wraps every network provider; the fake model stays bare. Both wrappers pass attribute lookups (`url`, `model`, `timeout`) to the client. Order: `FallbackLLM(CircuitBreaker(RetryingLLM(primary)), CircuitBreaker(RetryingLLM(fallback)))`.
- Model fallback (demo gap D6): `llm/fallback.py` `FallbackLLM(primary, fallback)` retries the same prompt on the fallback after any `LLMError` and logs `llm_fallback`; `get_llm()` builds it when `LLM_FALLBACK_PROVIDER` names a different provider (`llm/__init__._provider`). Per-provider `<PROVIDER>_TIMEOUT_SECONDS` override `LLM_TIMEOUT_SECONDS`. Measured: Groq free tier (about 8,000 tokens a minute) answers about one retail question a minute in about 2 s; later ones fall back to Ollama. The default stays Ollama.
- Token budget (demo gap D5): `llm/budget.py` `TokenBudget(limit, window_seconds, per_user, clock)` is a rolling window (default an hour) with a per-user share; `make_generate` charges `request.state.user`. Exhausted raises `LLMBudgetError` (a `LLMRateLimitError`) → 429 "The question limit for this hour has been reached." Settings: `LLM_TOKEN_BUDGET` (400000), `LLM_USER_TOKEN_BUDGET` (150000), `LLM_TOKEN_BUDGET_WINDOW_SECONDS` (3600). Tests inject a clock.
- Injection (GR-INJ-01/02/03): `app/prompt_safety.py` `fence(label, text)` and `FENCE_NOTE` in the SQL, rewrite, explain and knowledge prompts (prompt openings unchanged for `RoutedLLM`; the repair prompt keeps its sql code fence); `output_problem(answer)` checked in `analyst.ground` and `check_citations` (fallback, `answer_fallback` log). `retail.generate.INJECTED_PRODUCT` and `INJECTED_CAMPAIGN` rename rows after generation, so numbers never change.
- Assumptions and causal language (GR-ACC-03/04): `app/bi/assumptions.py` (dates and filters from the SQL; `/ask` returns `assumptions`; the UI shows them); `analyst.asks_why`/`claims_a_cause` replace a causal answer to a why-question on the data path with the plain answer plus "The data shows what happened, not why." No clarifying questions (decision in guardrails.html 7n).
- Alerts (GR-OBS-02): `app/alerts.py` `evaluate(events, tokens_last_day, now)` is pure (four rules, thresholds from `ALERT_*`); `audit.recent_events`/`tokens_since` read with `ALERTS_DATABASE_URL` (the `audit_reader` login from `db/init/11_audit_reader.sql`, applied by `setup.sh`). `main.unexpected_error_handler` turns any unplanned exception into a plain 500 audited as `server_error` (class only). Tests that need the 500 use `TestClient(app, raise_server_exceptions=False)`.
- Guardrail events (GR-OBS-01): `audit_event` adds `latency_ms` from `request.state.started`; blocking events carry `guardrail` and `category`. New validator rejections must pass `guardrail=`/`category=` to `SQLRejected` (default `GR-SQL-01`/`statement`); new guardrails audit with their ID. Non-GR controls use the names `role-access`, `login-throttle`, `step-limit`, `token-budget`, `statement-timeout`.
- Exports (GR-PRIV-05): roles have `export` in the policy (`Role.export`, default false, both roles true); `access.may_export`; `POST /exports` audits `export` (or `export_denied`, 403). The UI's `export_table` posts first and shows `st.download_button` only after the backend recorded it.
- Small groups (GR-PRIV-03): `app/bi/small_groups.py` `with_customer_count(sql)` adds `COUNT(DISTINCT <t>.customer_id) AS bi_group_customers` to aggregated single-SELECT queries that read a table with `customer_id` (customers preferred; CTEs, set operations and window queries are skipped); `sql.execute` validates and runs that instead (fail closed), and `suppress_small_groups` removes rows with 1 to k-1 customers (0 = guests only, kept) and drops the helper column; `suppressed_groups` in `/ask`, a note in the answer. `[sql] min_group_customers = 5`; `limits.privacy_min_group()` lets the environment only raise it. Catalog sources only.
- Privacy (GR-PRIV-01/02/04): `app/privacy.py` (`redact_text`, `redact_rows` with the catalog's `pii` column names, `redact_value` for logs and audit). `analyst.explain` sends redacted rows (logs `privacy_redacted` with a count); grounding still uses the real rows. `JsonFormatter`, `RedactingFormatter` and `audit.record` mask every value; `db_error` logs the error and cause class names only, never Postgres's message. `LLM_PROVIDER_DATA_POLICY` (`deny` default, `zdr`, `allow`) adds OpenRouter's `provider` options; Groq with `zdr` needs `GROQ_ZDR_CONFIRMED=true`; `llm_data_policy` is logged when the model is built. Phone patterns must not match dates or amounts (tests list both).
- Per-user limits (GR-COST-01/02/03): `app/request_limits.py` `RateLimiter.hit(user)` (questions per minute and day on a ledger; a refused question is not counted) and `MemoryRunning.hold(user)`; `appdb.PgRunning` (stale holds expire after 300 s) and `PgTokenLedger("request_usage")` with `STATE_STORE=postgres` (`db/init/10_request_limits.sql`). `main.question_limits` (a yield dependency) guards `/ask`, `/ask/sql`, `/chat`; `RateLimited` and `Busy` → 429, audited `rate_limited` with `guardrail` and `reason`. Daily tokens: `TokenBudget(per_user_daily=...)` raises `LLMDailyQuotaError`. Tests get a generous limiter from the `generous_request_limits` conftest fixture; `evals/demo.py` installs one too.
- Cost check (GR-SQL-03): `db._check_cost` runs `EXPLAIN (FORMAT JSON)` for every `ValidatedSQL` inside `run_readonly`'s transaction; `plan_problem` compares the total cost and the largest row estimate of any plan step with `[sql] max_plan_cost`/`max_plan_rows` (`limits.sql_max_plan_cost/rows`). Raises `QueryTooExpensiveError` (422, audited `sql_rejected` with `guardrail`, `category`, `estimate`); not repaired. Re-tune the limits on the full retail data when it grows (legit max cost 81,373, rows 616,532).
- Request deadline (GR-WF-02): `answer_question` sets `Context.deadline` from `[sql] deadline_seconds` (300; `REQUEST_DEADLINE_SECONDS` lowers it); `service._traced` raises `DeadlineExceeded` before starting any step after it (504, audited `deadline_exceeded`). A running model call is bounded by its own timeout, not interrupted. The provider back-off half of GR-WF-02 is D9's circuit breaker.
- Step limit (demo gap D1): `[sql] max_steps = 15` (`limits.workflow_max_steps()`, `WORKFLOW_MAX_STEPS` lowers it) is passed to LangGraph as `recursion_limit`; `GraphRecursionError` becomes `service.StepLimitError` → 422, audited `step_limit`. The installed LangGraph does not stop at 25 steps by default (a broken repair counter looped 1,001 model calls), so never rely on its default. The longest legitimate path is 13 steps (pinned by `test_the_longest_legitimate_path_fits_within_the_limit`); adding a step to it means re-checking the cap.
- `app/knowledge/context.py` (RAG R6a): `knowledge_for(question, role)` retrieves only on catalog sources and returns `[]` on `EmbeddingError` or `store.KnowledgeUnavailable` (logged), never failing a question. `main.get_knowledge` is the FastAPI dependency. `text_to_sql.knowledge_text` fences hits in `<<<knowledge ... >>>` (a `>>>` inside content is broken up) in the SQL prompt only; knowledge stays out of the explain prompt so the numbers check is unchanged. `/ask` returns `sources`; the `ask` audit event lists their IDs. Only `store.py` imports the driver for the index (GR-SQL-06).
- `backend/policy/guardrails.toml`: the guardrail policy (SQL limits, function allowlist, blocked prefixes, and `[sources.<name>.roles.<role>]` with tables, login variable and `personal_data`). `DATA_SOURCE` (default `sample`) picks the source; `access.tables_for`, `db_env_for`, `uses_catalog` and `denied_columns` read it on every call. For the retail source the prompt's schema comes from the catalog (`schema._catalog_text`, cached; call `schema.clear_cache()` in tests) and the validator refuses `denied_columns`. `app/policy.py` loads and strictly validates it at import, so a malformed file stops the backend (fail closed); `access.py`, `limits.py` and `sql_guard.py` read it. Edit rules there, not in Python. Environment variables may only lower its limits.
- `backend/app/main.py`: routes, exception handlers (each maps to a generic client message; details go to logs with the request ID), request-ID middleware, `make_generate` (token budget + logging around every LLM call), `conv_key`.
- `auth.py` (argon2, JWT HS256, `current_user`), `appdb.py` (users table in `appdb`), `cli.py` (create-user), `access.py` (`ROLE_TABLES`, `ROLE_DB_ENV`, `AccessError`).
- `db.py`: `run_readonly(sql, params, max_rows, timeout_ms, role)` — the role picks the database login; read-only transaction, statement timeout, row and byte caps, read through a server-side cursor in batches (limits from `limits.py`, environment `SQL_MAX_ROWS`, `SQL_MAX_RESULT_BYTES`, `SQL_TIMEOUT_MS`). It accepts only `ValidatedSQL` (from `validate_sql`) or `TrustedSQL` (fixed code-authored text, never model or user text), both in `sqltypes.py`; anything else raises `UnvalidatedSQLError`.
- `llm/`: `LLMService` interface, `openrouter.py` (any OpenAI-compatible chat API; OpenRouter by default, Groq with `LLM_PROVIDER=groq`, `GROQ_API_KEY`, `GROQ_MODEL` (default `qwen/qwen3.8-27b`), or Ollama with `LLM_PROVIDER=ollama`, `OLLAMA_BASE_URL`, `OLLAMA_MODEL`). The evaluation runner retries provider rate limits with `with_backoff`; the app does not, `fake.py`, `budget.py`, typed errors (timeout, rate limit, config, generic).

## Decisions to preserve

- Defense in depth for SQL: prompt shows only the role's tables → validator (one SELECT or set operation of SELECTs; no write, command or `INTO` node anywhere, including CTEs; no locking; allowed tables; no schema-qualified tables or functions; **functions only from the allowlist** in `sql_guard.py`, never a blocklist; every join linked by a condition unless one side is a one-row aggregate; at most `SQL_MAX_TABLES` tables and `SQL_MAX_DEPTH` nesting) → per-role read-only login. `SQLRejected.user_message`, when set, is the only rejection text shown to users. The database role is the real enforcement.
- Widening the SQL function allowlist is a security change: add an acceptance test and run the real-model evaluation.
- Roles: `analyst` → `orders`, `regions`; `limited` → `regions`. The role comes from the users table on every request, never from the token's claims. Unknown roles raise `AccessError` (403), never fall back.
- Every number in a model-written answer must appear in the result or question; otherwise use the plain fallback. One-row results containing NULL count as no data. Totals and percentages belong in deterministic code.
- Charts come from `bi/chart.py` rules: the spec has the suggested `type`, the `options` that fit (suggestion first) and the column roles (`x`, `y`, `series`, `values`, `size`, `location`, `start`, `end`). The frontend draws only offered types (Plotly, `frontend/charts.py`) and lets the user switch between them. The model never picks a chart. Funnel needs a stage-like label column; shapes are recognised in any column order. A chart type named by the user (`requested_chart`, whole-word patterns) becomes the suggestion if it fits, else `chart_note` explains; chart-only messages (`is_chart_only`) are answered in `main.redraw` from the last turn, with no model call or query, audited as `chart_change`.
- Conversations are in memory, capped, keyed `username:conversation_id`; another user's ID returns 404, not 403.
- The Streamlit token lives only in server-side session state; refresh signs the user out.

## Testing conventions

- `tests/conftest.py` sets local database URLs and `JWT_SECRET`, and signs every test in as `test-analyst` by overriding `current_user`. Auth tests remove the override to test the real check. It also overrides `get_knowledge` (the `no_knowledge` fixture) so no test reaches Ollama or the real index; tests that want knowledge override it again.
- `tests/routed_llm.py` is the scripted model: it answers by prompt type (`Rewrite…` → rewrite, `You write PostgreSQL…` → SQL, else → answer). Keep those prompt openings stable or update `RoutedLLM`.
- Tests run on the sample source (`conftest.py` removes `DATA_SOURCE` and points the retail login variables at `retail_test`); retail tests set `DATA_SOURCE=retail` with `monkeypatch` and clear the schema cache.
- `db.py` classifies Postgres errors: `DBQueryError` (SQLSTATE class 42 or 22, a wrong query, 422), `DBAccessError` (permission denied, 403), `DBTimeoutError` (504), other `DBError` (503).
- Tests that call `run_readonly` directly to test the database layer wrap their SQL in `TrustedSQL`. `tests/test_execution_path.py` lists the public routes; every other route must depend on `signed_in`.
- Mark tests that need the database `@pytest.mark.integration`. Stand-ins for `generate_sql`/`run_readonly` accept `**kw`.
- Run the real-model evaluation (`evals.run`) after any change to prompts, the model, the validator, the workflow graph or the dataset, and before accepting a new baseline. It exits 1 on any safety failure, data change or regression against the model's own baseline (`evals/baselines/<model>.json`), and 2 if any case could not be scored because the provider failed (such a run never updates the baseline). Reports go to `evals/reports/` (git-ignored).
- Prompt changes can make the model over-refuse. After editing `build_prompt`, run the real-model evaluation; the decline wording must state what always gets a query before saying when to decline.

## Gotchas already hit

- The database image is `pgvector/pgvector:pg16-trixie`, not `pg16`: it matches the earlier `postgres:16` exactly (Debian 13, glibc 2.41). A different glibc can silently break text sorting and indexes on an existing data volume. Back up first (`backups/` is git-ignored; dumps contain password hashes).

- `information_schema.key_column_usage` (and `table_constraints`) list keys only for tables the login owns; read-only logins see none. Read keys from `pg_constraint`.

- Docker Compose gives shell variables priority over `.env`. If `.env` was loaded with `set -a; source .env` before starting a session, a changed `.env` value is ignored; start Compose with `env -u NAME docker compose up -d` or a fresh terminal.
- Before appending to `.env`, make sure it ends with a newline, or the new line is glued onto the last variable (it once corrupted `JWT_SECRET`). Back it up first and never print its contents.

- Postgres evaluates constant expressions such as `1 / 0` while planning, even inside `CASE`; a test that needs an error on a later row must make it depend on the row (`1 / (g - g)`).
- New limits are read in `app/limits.py`; add each one to `docker-compose.yml` too, or a value in `.env` never reaches the container.

- The retail analyst login has column-level grants, so `SELECT *` on `customers`, `customer_addresses` or `employees` is refused by the database. Prompts and the catalog must list allowed columns only.
- Retail integration tests rebuild `retail_test` only; never point tests at `retail`.

- Inside Compose, use service names (`http://backend:8000`, `db:5432`); host port 5433 exists only outside Docker.
- A missing `environment:` entry (e.g. `BACKEND_URL` on the frontend) silently falls back to `localhost`.
- Each `.gitignore` entry needs its own line.
