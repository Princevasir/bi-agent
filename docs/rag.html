BI Agent RAG: knowledge retrieval for business questions

Retrieve business knowledge (definitions, rules, validated SQL, dashboards, data-quality notes, incident reports) to help the agent understand questions; keep using SQL for every number.

Status: plan approved 24 October 2026; R1 done (knowledge pack and loader); R2 done (pgvector and the knowledge schema); R3 done (embedder); R4 done (ingestion: 64 documents, 77 chunks in the index); R5 done (retrieval: Recall@5 0.947, MRR 0.939); R6 next. Companion to build-plan.html, guardrails.html and data-catalog.html.

Principle

RAG retrieves knowledge: what "active customer" means, which revenue definition is authoritative, the fiscal calendar, proven query patterns, what happened to tents in March 2026. SQL retrieves data. Vector search never replaces the query engine, and no number in an answer comes from a document.

Current architecture (inspected 24 October 2026)

  • One fixed LangGraph workflow (bi/service.py): rewrite, write SQL (second opinion on declines), validate, execute, explain, ground, with one bounded repair. The model is called in three places only; it never chooses tools.
  • Schema knowledge is structured, not embedded: catalog/*.toml plus database introspection, filtered per role, and the whole role catalog goes into every SQL prompt (about 4,700 tokens).
  • Business rules exist in part: 6 metrics, 2 enforced metric rules, SQL hints; none versioned or owned.
  • LLM: one OpenAI-compatible client, now pointed at local Ollama (qwen2.5-coder:7b). Storage: Postgres 16 (retail, appdb, analytics). Tests: pytest, Streamlit AppTest, real-model evaluation with per-model baselines.

Data model (appdb, schema knowledge)

documents (id from the file path, type, title, source, domain, owner, version, effective date, status, access groups, content hash, updated at); chunks (id, document, position, content, hash, token count, vector(768) embedding, embedding model); ingestion_runs (counts and errors). Unchanged hashes are not re-embedded; a changed document replaces its chunks in one transaction; deleted files leave the index; superseded versions are never retrieved; duplicate content is refused; mixing embedding models is refused.

Risks

  • The local 7B model limits accuracy; R7 measures how much RAG helps and makes a stronger model a one-setting comparison.
  • Two embedding services over time (local now, hosted on AWS); the interface and the "never mix models" rule keep this safe.
  • The database image change; same Postgres 16 and a backup first.
  • Prompt injection through documents; retrieved text is fenced and treated as data.
