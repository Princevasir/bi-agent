BI Agent guardrails: assessment, specification and roadmap

What can go wrong when an LLM writes SQL against company data, what already stops it, what doesn't, and the order in which we close the gaps, one tested guardrail at a time.

Status: GR-SQL-01, GR-SQL-06, GR-SQL-04 and GR-SQL-02 implemented and verified on 23 October 2026 (sections 6, 7b, 7c and 7d), GR-POL-01 (7e) and GR-POL-02 (7f). Order revised the same day to add the policy file and generated prompt rules (section 4). Assessment written the same day before any code changed. Every "confirmed" finding below was reproduced by running the input against the real code or database on the owner's Mac on that date; "potential" findings are reasoned from the code and still need a test. Not risks today, by design: unbounded agent loops and unauthorized tool calls (the workflow is a fixed graph; the model calls no tools); retries without limit (there are none); cross-user cache leakage (there is no result cache). Any future change that adds tools, loops or caching must add guardrails for them.

4. Two layers: guidance and enforcement

A reliable agent needs both, and they do different jobs. Guidance (instructions in the prompt) makes the model get it right the first time; without it the system is safe but keeps rejecting queries the model could have written correctly. Enforcement (validator, execution limits, database grants) makes a wrong or manipulated answer harmless; it works whatever the model does. Guidance lowers how often things go wrong; enforcement decides what happens when they do. Nothing safety-critical may depend on guidance alone.

One source for both (decided 23 October 2026): the rules live in one reviewed policy file, backend/policy/guardrails.toml. The code reads it for enforcement (GR-POL-01), and the SQL prompt's rules section is generated from it (GR-POL-02), so what the model is told and what the code enforces cannot drift apart. The model never reads the file as instructions to obey; it only sees the generated rules. A malformed policy stops the backend from starting (fail closed). Environment variables may tighten a numeric limit but never loosen one, and never change functions, tables or roles. One bounded retry with the plain rejection reason (GR-WF-01) closes the loop when the model still breaks a rule. Progress is measured by the evaluation's first-attempt rejection rate, which should fall while safety results stay at 100%.

4b. Guardrail specification

Every guardrail has an enforcement point outside the model, a failure behaviour, configuration, logging, tests and measurable acceptance criteria. Limits live in one settings module (app/limits.py, read from the environment) rather than scattered constants.

6. First guardrail: GR-SQL-01, validator allowlist

Why first: it is the only finding where a defense layer is confirmed to be skipped (R1, R2), it also removes the cost-bomb and information-disclosure functions (R3 in part, R7) and a false rejection (R14), it touches one file, adds no dependency, and every later SQL guardrail builds on the same tree walk.

Files: backend/app/bi/sql_guard.py (logic), backend/tests/test_sql_guard.py (tests). No other component changes. Then the real-model evaluation, as the project rules require after any validator change (about 30,000 tokens with --repeat 3).

Design:

  • Top level must be exp.Select or a set operation of selects; anything else is rejected as today.
  • Walk every node: any Insert, Update, Delete, Merge, Create, Drop, Alter, Command, Into or locking clause anywhere (including inside CTEs and set-operation branches) is rejected.
  • Every function node (sqlglot's typed functions and unknown Anonymous ones alike) is mapped to a lower-case name and must be in ALLOWED_FUNCTIONS: aggregates (count, sum, avg, min, max, stddev, percentile_cont…), conditional (coalesce, nullif, greatest, least, case), maths (round, abs, ceil, floor), date and time (date_trunc, extract, to_char, date_part, now, current_date, make_date, age), strings (lower, upper, trim, length, concat, substring, replace with no padding or repeat functions), casts, and window functions (row_number, rank, dense_rank, lag, lead). Schema-qualified function names are rejected.
  • Table-valued functions in FROM (today a confusing "Table not permitted:" with an empty name) get a clear message.
  • Kept unchanged: one statement, table allowlist, no schema-qualified tables, CTE names. The old prefix blocklist becomes redundant but stays as a second check until the allowlist has run in the evaluation.
  • Risk: sqlglot's internal class names can change between versions (the requirement is sqlglot>=25, unpinned until M25). The tests that validate every evaluation reference query catch that.

Configuration: the allowlist is code, reviewed like code, not an environment variable: widening it is a security decision.

7b. GR-SQL-06: one execution path

Problem: run_readonly accepted any string, so a future route, tool or refactor could send model SQL to the database without the validator, and /ask/sql already returned model SQL nobody had checked (R12).

Design: two marker types in backend/app/sqltypes.py. 7c. GR-SQL-04: bounded result reading

Problem (R4): run_readonly used a client-side cursor, so Postgres computed and sent the whole result and the backend held it in memory before keeping 200 rows.

Design: a server-side (named) cursor read in batches of 50 until the row cap plus one or the byte limit is reached, then closed with the transaction. Bytes are counted as the JSON size of the rows returned. If the very first row is over the byte limit, ResultTooLargeError is raised and the API answers 422 "The result is too large to show. Try a narrower question.", audited as result_too_large. Limits come from a new settings module, backend/app/limits.py, read at call time; a non-numeric or non-positive value raises instead of silently using a default. The ask audit event already recorded truncated.

Configuration: SQL_MAX_ROWS (200), SQL_MAX_RESULT_BYTES (1,000,000), SQL_TIMEOUT_MS (5,000); passed through docker-compose.yml.

7d. GR-SQL-02: query structure limits

Problem (R3): a join with no join condition multiplies tables together (three copies of a 281k-row table is about 2.2 × 1016 rows), and very wide or deeply nested queries are slow and usually a sign the model misunderstood the question.

Design (in validate_sql, after the function check): every join in every SELECT, including inside CTEs and subqueries, must have a condition. A join has one if it uses USING or NATURAL, or if its ON (or, for an old-style comma join, the WHERE) compares a column of the joined table with a column of another table. ON true, ON 1 = 1 and comparisons within one table do not count. The one exception is a source that returns exactly one row (an aggregate with no GROUP BY, directly or through a CTE), the usual way to compute a share of a total. Table references (repeats counted, CTE names not) are capped at SQL_MAX_TABLES, and SELECT nesting at SQL_MAX_DEPTH; set-operation branches are not nesting. These rejections carry a user-facing message, "The generated query was too broad to run safely. Try a more specific question, for example a shorter period or one grouping."; all other rejections keep the generic one.

Configuration: SQL_MAX_TABLES (8), SQL_MAX_DEPTH (3), in limits.py and docker-compose.yml.

7e. GR-POL-01: one policy file

Problem: the rules lived in four Python files (sql_guard.py, limits.py, access.py, the Compose defaults), so reviewing "what may the agent do" meant reading code, a typo could silently weaken a rule, and nothing tied the prompt to the enforcement.

Design: backend/policy/guardrails.toml holds the SQL limits, the function allowlist, the blocked prefixes and the roles (tables and database login variable). app/policy.py loads it with Python's built-in tomllib (no new dependency) and checks it strictly. access.py, limits.py and sql_guard.py read their rules from it under the same names as before, so no caller changed. Because they read it when imported, a malformed policy stops the backend from starting. Environment variables now tighten only: SQL_MAX_ROWS=500 is ignored when the policy says 200, SQL_MAX_ROWS=50 applies. The backend logs policy_loaded with the file's path and SHA-256 hash at start-up, so a log line shows exactly which policy was in force. The Dockerfile copies the policy into the image; GUARDRAIL_POLICY can point elsewhere.

7f. GR-POL-02: prompt rules generated from the policy

Problem: the validator enforced rules the model was never told, so a correct question could fail on a rule one sentence would have prevented.

Design: text_to_sql.rules_text() builds a short "Rules" section from the policy at call time: read only (no writes, even inside WITH), every join linked by a condition (no cross joins except to a one-row total), the table and nesting limits, no schema-qualified names or table functions, and the list of allowed functions. The policy gained prompt_functions, the SQL names shown to the model (the validator matches sqlglot class names, which the model would not know); a test calls every one of them through the validator, so the prompt never offers a function enforcement rejects. The evaluation report gained a count of validator rejections in attempts where a query should run.

8. Operational notes (grows with each guardrail)

  • Investigating an incident: take the X-Request-ID from the response or the user, search the JSON logs for it, then SELECT * FROM audit.events WHERE request_id = '…' in appdb as admin. Guardrail events will carry a category and guardrail ID.
  • Changing a policy safely: change the list or limit in code or .env; add or update the test first; run the backend suite; run the real-model evaluation including the adversarial set; record both runs in the build plan; commit with the guardrail ID in the message.
  • Changing the policy (GR-POL-01): edit backend/policy/guardrails.toml, not Python. The backend refuses to start if the file is malformed; check the start-up log for policy_loaded and the new hash. Environment variables can only lower its limits.
  • Widening the SQL function allowlist (GR-SQL-01): add the sqlglot class name to allowed_types in the policy file (find it with type(f).__name__ on the parsed query) or the SQL name to allowed_names; add an acceptance test; confirm the function cannot run SQL from a string, read files or settings, or build unbounded values; run the backend suite and the real-model evaluation.
  • Adding a database query in code (GR-SQL-06): model or user text must go through validate_sql; fixed text written in code is wrapped in TrustedSQL and must never include model or user text (use query parameters for values). A new route must depend on signed_in or be added deliberately to the public list in tests/test_execution_path.py.
  • Configuration: each guardrail's settings are listed in its specification above and will be collected in the README configuration table as they are built.

9. Questions before implementation

  • Approve the order? Validator first (confirmed bypass), cost limits raised to before the catalog.
  • Allowlist strictness: reject any function not on the list, accepting that an occasional valid model query may be rejected (the evaluation will show it), rather than allow unknown functions?
  • Row-level and tenant rules: is this one company with no tenants? Should any role see only some rows, for example store managers only their own store? (Affects M29 and the retail grants.)
  • Export: should users be able to download result tables (Streamlit offers it by default), and should that be recorded?
  • Still open from the earlier draft: minimum group size on or off; clarifying questions allowed; default limits (10 per minute, 200 per day, 100,000 tokens per user per day).
