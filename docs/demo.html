BI Agent: ask your business data in plain English

A natural-language analytics assistant, demonstrated on a generated dataset for a fictional outdoor retailer. You ask a question; it returns a grounded answer, the SQL it ran, a table and a chart. It uses business knowledge (RAG) to get definitions right, and it is safe by design.

The problem

Business people have questions; the answers sit in SQL

Without the agent

A manager asks "What was revenue by region last fiscal year?" and waits for an analyst, who must know which orders count, how regions are assigned and when the fiscal year starts.

The naive AI fix fails

"Send the question to an LLM and run its SQL" gives confident wrong numbers (averaging order lines instead of orders), can leak personal data, and can be talked into destructive queries.

What this system guarantees

  • SQL only runs after a validator and on a read-only login for the user's role
  • Every number in an answer comes from the query result
  • Business definitions come from owned, versioned documents

System design

Architecture

Everything runs in Docker Compose (Postgres 16 with pgvector, backend, frontend); the models run locally in Ollama.

The five layers

Mapping the project to the five layers of an AI system

Agents and orchestration

Five specialist agents, routed by a coordinator

LLM

Coordinator

Understands each message, rewrites follow-ups ("And August?") into a standalone question, and routes it to the right agents.

code

Knowledge

Finds the business knowledge a question needs (RAG) and answers questions about the data catalog.

LLM code

SQL

Writes one read-only query, has it validated (by code, never the model) and runs it on the role's login; one repair, one second opinion.

LLM code

Analyst

Explains the result in a sentence; if any number is not in the result, replaces it with a plain answer from the rows.

code

Chart

Chooses a chart by fixed rules and redraws the last result on request ("make it a pie chart") without the model.

Pattern

Sequential pipeline with conditional routing (LangGraph). Steps must happen in order, so this is the simplest pattern that fits, and each step is easy to test.

Coordinator→ Knowledge→ SQL→ Analyst→ Chart

Data question: all five. Chart change: Coordinator → Chart. Question about the data: Coordinator → Knowledge. Declined message: Coordinator → Knowledge → SQL. The LLM never decides what may run.

Design decisions

The four decisions

D1 Agent boundaries

  • Each agent owns named graph steps; a test checks every step belongs to exactly one agent
  • Tests check that only the SQL agent touches the database, and that the Knowledge and Chart agents never call the model
  • The validator, not the model, decides what runs

D2 Communication

A shared typed state object (LangGraph StateGraph with a TypedDict). Conversations are kept per user for follow-ups ("And August?").

D3 Error boundaries

  • Bad SQL: one repair with the error, then a clear message
  • Model declines a real question: one second opinion
  • Knowledge index down: answer without knowledge
  • Model writes an ungrounded sentence: fall back to a plain answer from the rows

D4 Termination

  • Every loop has a counter from the policy file: repair_attempts = 1, decline_retries = 1
  • A hard cap of max_steps = 15 workflow steps per question (the longest normal path takes 13); a run that reaches it is stopped and audited
  • Stops when the output validates, when no rows come back, or when the question is declined
  • Timeouts on the model and the database

Irrelevant documents are filtered out

Relevant matches scored at least 0.649 and off-topic questions ("hello", the weather, a poem) at most 0.556. With the threshold at 0.60, off-topic questions retrieve nothing and precision rose from 0.274 to 0.324.

Access control in retrieval

A limited user never receives documents about tables they cannot query, and superseded versions of a rule are never retrieved. Both are checked by tests.

Error handling

The unhappy path was built first

What goes wrongWhat the user sees
The model writes invalid or unsafe SQLOne automatic repair using the error; if that fails, "The generated query was rejected." (422)
The model returns text instead of SQLTreated as a rejection, never executed
The model declines a real data questionOne second opinion; then a friendly explanation of what it can answer
The model fails briefly (throttled, 5xx, dropped connection)One automatic retry after a short pause
The model keeps failingA circuit breaker skips it for a minute: the fallback model answers at once, or a plain "temporarily unavailable" (503) instead of another long wait
The model times out or is rate-limitedWith a fallback configured, the local model answers instead (logged); otherwise 504 or 429 with a plain message
The model invents a number in its sentenceThe grounding check replaces it with a plain answer built from the rows
The embedding model or knowledge index is downThe question is answered without knowledge; a warning is logged
The database is down or slow503 or 504; statement timeout; /ready reports which database is down
A query returns millions of rowsRead in batches through a server-side cursor, capped by rows and bytes
Too many tokens are usedA rolling hourly budget, in total and per user, pauses model calls (429) and refills on its own
Someone guesses passwordsFive failures lock the account for 15 minutes (429)

Safety

Defence in depth: the LLM never enforces authorisation

Prompt shows only the role's tables→ Validator (sqlglot)→ Read-only login per role→ Audit trail

Validator

  • One SELECT (or a UNION of SELECTs); no writes anywhere, not even in WITH
  • Allowed tables and columns only; personal-data columns refused
  • Functions from an allowlist only
  • Joins must be linked; table and nesting limits
  • Metric rules, e.g. revenue must exclude cancelled orders

Roles

  • analyst: all retail tables except personal-data columns
  • limited: geography and products only
  • The role is read from the users table on every request, never from the token

One policy file

backend/policy/guardrails.toml holds every limit and rule. The prompt's rules and the validator's checks come from it, so they cannot drift apart. A broken file stops the backend.
